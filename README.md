# Akamai Bot Manager v2 Solver — Basic-Fit

Reverse-engineered Akamai BM v2 behavioral challenge solver for `login.basic-fit.com` / `my.basic-fit.com`.

Three solver modes, from lightest to heaviest:

| Solver | File | RAM/session | Browser needed? | Description |
|--------|------|-------------|-----------------|-------------|
| **jsdom** (default) | `solver_jsdom.py` | ~5 MB | No | Pure API. Sensor data generated by jsdom + fpgen fingerprints. All HTTP via curl_cffi. |
| **pool** | `solver_pool.py` | ~20 MB | Yes (shared) | One persistent Chrome process, lightweight contexts per solve. |
| **api** | `solver_api.py` | ~150 MB | Yes (per-solve) | New Chrome instance per solve. Most robust, highest RAM. |

## How It Works

### Akamai BM v2 Overview

Akamai Bot Manager v2 protects endpoints with multi-layered detection:

1. **TLS Fingerprint** — JA3/JA4 fingerprint checked at the edge. Wrong TLS = instant 403.
2. **Sensor Script** — ~560KB obfuscated JavaScript loaded on every page. Collects 200+ browser attributes (canvas, audio, WebGL, fonts, plugins, screen, navigator, etc.) plus behavioral data (mouse, keyboard, touch events). Posts sensor data to the same URL it was loaded from.
3. **`_abck` Cookie** — Trust score. `~0~` = trusted, `~-1~` = untrusted. Tied to the TLS fingerprint — cookies from one TLS stack are rejected when presented via a different stack.
4. **`sec_cpt` Cookie** — Challenge state machine (1→2→3→4). See below.
5. **Server-Side Checks** — TLS fingerprint, HTTP/2 fingerprint, `sec-ch-ua` vs `User-Agent` consistency, IP reputation, sec-fetch-* header presence.

### Cookie Map

| Cookie | Purpose | Set By |
|--------|---------|--------|
| `_abck` | Bot detection trust. `{hex}~{trust}~{data}~{score}~{...}` | Akamai edge |
| `bm_sz` | Session metadata + counter for sensor data. `{hex}~{data}~{counter}~{hash}` | Akamai edge |
| `ak_bmsc` | Bot Manager session cookie | Akamai edge |
| `sec_cpt` | Challenge state machine. `{data}~{state}~{...}` | Akamai edge |
| `_csrf` | CSRF token for login form | Application |

### The 428 Challenge Flow

Even with trust=0, the first login POST always returns 428 with a behavioral challenge:

```
Client                          Akamai Edge                    Origin Server
  |                                 |                              |
  |-- POST /login ----------------->|                              |
  |<-- 428 + challenge JSON --------|                              |
  |    {sec-cp-challenge: true,     |                              |
  |     chlge_content_url: "...",   |                              |
  |     verify_url: "..."}          |                              |
  |                                 |                              |
  |-- GET challenge page ---------->|  (sec_cpt: 1 → stays 1)     |
  |<-- Challenge HTML + AKCPT.js ---|                              |
  |                                 |                              |
  |-- Sensor POSTs (from script) -->|  (sec_cpt: 1 → 2)           |
  |                                 |                              |
  |-- POST verify URL ------------->|  (sec_cpt: 2 → 3)           |
  |<-- 403 (but cookie advances) ---|                              |
  |                                 |                              |
  |-- POST /login (retry) --------->|                              |
  |                                 |-- (sec_cpt=3, passes) ------>|
  |<-- 200/401 (real response) -----|<-- login result -------------|
  |                                 |  (sec_cpt → 4)              |
```

### sec_cpt State Machine

| State | Meaning | How to advance |
|-------|---------|----------------|
| 1 | Challenged | Load `chlge_content_url`, let sensor script run |
| 2 | Sensor accepted on challenge page | POST to `verify_url` with `{"sensor_data": ""}` |
| 3 | Verification accepted | Retry the protected request |
| 4 | Fully passed | (set after successful retry) |

Key insight: the POST to `verify_url` returns **403**, but `sec_cpt` still advances. Parse the cookie, not the status code.

## Architecture

### jsdom Solver (`solver_jsdom.py`)

Zero browser overhead. Uses jsdom as a headless JS engine to run Akamai's sensor script, with fpgen-generated fingerprints for environment fidelity.

```
solver_jsdom.py
├── solve(email, password)
│   └── _attempt() (up to 3 retries)
│       ├── fpgen.generate(browser="Chrome", os="Windows")
│       │   └── Generates: UA, sec-ch-ua, screen, GPU, WebGL params,
│       │       500 audio signal floats, fonts, plugins, memory limits
│       ├── curl_cffi session (impersonate="chrome131")
│       ├── GET login page → _abck, bm_sz cookies
│       ├── GET sensor script
│       ├── node jsdom_sensor_gen.js <cookies> <script> <fingerprint>
│       │   ├── Creates JSDOM with full browser stubs from fpgen data
│       │   ├── Evaluates sensor script → script runs autonomously
│       │   ├── Simulates mouse/keyboard events
│       │   ├── Captures all XHR POST bodies (natural sensor flow, f1=0)
│       │   └── Returns all captured POST bodies
│       ├── Forward all captured sensor POSTs via curl_cffi
│       │   └── Headers: sec-fetch-dest, sec-fetch-mode, sec-fetch-site,
│       │       Accept-Language (critical for acceptance)
│       ├── POST /login → 428 challenge
│       ├── GET challenge page
│       ├── Generate + forward challenge sensors → sec_cpt=2
│       ├── POST verify URL → sec_cpt=3
│       └── Retry POST /login → 200/401
│
jsdom_sensor_gen.js
├── Environment stubs (from fpgen fingerprint JSON):
│   ├── navigator: UA, platform, languages, hardwareConcurrency, deviceMemory
│   ├── screen: width, height, colorDepth, pixelDepth
│   ├── window: inner/outerWidth/Height, devicePixelRatio
│   ├── WebGL: full parameter map from fpgen (getParameter responses)
│   ├── GPU: vendor + renderer from fpgen
│   ├── Audio: 500 real signal floats from fpgen (AudioContext + OfflineAudioContext)
│   ├── Canvas: node-canvas 2D context (optional)
│   ├── chrome: runtime, loadTimes, csi
│   ├── performance: timing, memory, now()
│   └── Hides: process, module, exports, require, Buffer, __filename, __dirname
├── XHR stub: captures POST bodies without making real HTTP requests
├── Event simulation: mousemove, mousedown/up, click, keydown/up
└── Output: JSON with all captured sensor POST bodies
```

### Playwright Pool Solver (`solver_pool.py`)

One persistent Chrome process shared across all solves. Each solve creates a lightweight browser context (~20MB).

```
solver_pool.py
├── BrowserPool (singleton, thread-safe)
│   ├── One Chrome process (~150MB base)
│   ├── Dynamic UA detection (HeadlessChrome → Chrome)
│   └── new_context() → lightweight context per solve (~20MB)
├── page.route("**/*") → _route_through_cffi()
│   ├── Blocks analytics, fonts, tracking, images
│   └── Forwards essential requests through curl_cffi
└── All HTTP through curl_cffi → consistent Chrome TLS
```

### Per-Solve Solver (`solver_api.py`)

New Chrome instance per solve. Most isolation, highest RAM.

```
solver_api.py
├── New Playwright + Chrome per solve (~150MB)
├── Same routing architecture as pool solver
└── Same curl_cffi TLS consistency approach
```

## Sensor Data Format

### POST Body

```json
{"sensor_data":"3;0;1;0;4405315;8imztri69jZ...=;53,0,0,2,5,0;4a/S\")5J\"G..."}
```

Sent with `Content-Type: text/plain;charset=UTF-8`.

### Header Fields

```
{version};{f1};{f2};{f3};{counter};{hash};{counts};{encoded_body}
```

| Field | Value | Meaning |
|-------|-------|---------|
| version | `3` | Protocol version, always 3 |
| f1 | `0` or `1` | **Environment validity.** 0 = real browser, 1 = anomalies detected |
| f2 | `1` | Sub-version |
| f3 | `0` | Always 0 |
| counter | from `bm_sz` | Session counter (second-to-last `~` field in bm_sz cookie) |
| hash | base64 | 32-byte session-derived hash, constant per session |
| counts | `a,b,c,d,e,f` | Event counters (see below) |
| body | encoded | Custom-encoded fingerprint + behavioral data |

### Count Fields

| Index | Meaning | POST #1 (init) | POST #2 (behavioral) |
|-------|---------|-----------------|----------------------|
| 0 | Fingerprint data points | ~53 | ~20 |
| 1 | Mouse events | 0 | ~180 |
| 2 | Keyboard events | 0 | 0 |
| 3 | Touch events | ~2 | 0 |
| 4 | Sensor POST count | ~5 | ~10 |
| 5 | Accumulated time (ms) | 0 | ~732 |

### f1 Flag (Critical)

`f1=0`: Valid browser environment. Server advances `_abck` trust on acceptance.

`f1=1`: Anomalies detected. Server accepts the POST (`{"success":true}`) but does NOT advance trust. This is how Akamai detects headless/emulated environments without blocking them outright.

### Server Responses to Sensor POST

| Status | Meaning |
|--------|---------|
| 200 | Sensor data accepted, `_abck` may be updated |
| 201 | Sensor data rejected (missing headers, invalid format, or format-level detection) |

### Why Replay Fails

Sensor data is session-bound:
1. Counter from `bm_sz` cookie
2. Hash derived from `_abck` cookie value
3. Timing data (performance.now offsets)
4. `_abck` cookie validated against TLS fingerprint

### bmak Public API

The sensor script exposes a global `bmak` object:

| Method | Purpose |
|--------|---------|
| `get_telemetry()` | Returns `a=&&&e={_abck}&&&sensor_data={base64}`. **Always produces f1=1** — it's a programmatic API, not the natural flow. |
| `form_submit()` | Hook for form submission events |

**Important**: `get_telemetry()` always returns f1=1 and counter=8888888 (sentinel values). The natural XHR POST flow from the sensor script produces f1=0 with real counters. The jsdom solver captures the natural XHR flow, not the get_telemetry API.

## Obfuscation Analysis

The ~560KB sensor script uses 4 layers of obfuscation:

### 1. Control Flow Flattening

Every function is a `do { switch(state) { ... } } while (state != exit)` state machine with 50-100+ cases.

### 2. String Table Indirection

All string literals stored in arrays (`gp`, `xL`, `xK`, `c1`, `BN`, `Vw`), accessed by computed key.

### 3. Numeric Constant Bootstrapping

All numbers derived from `+[]` (0) and `+!![]` (1).

### 4. XOR String Encoding

Strings in tables are XOR-encoded, decoded by function `Fp` at runtime.

## Key Discoveries & Lessons

### What Worked

1. **sec-fetch headers are mandatory.** Sensor POSTs without `sec-fetch-dest: empty`, `sec-fetch-mode: cors`, `sec-fetch-site: same-origin` get 201 (rejected), even with valid f1=0 sensor data. This was the final breakthrough for the pure API solver.

2. **Natural XHR capture beats get_telemetry().** The sensor script's autonomous XHR POST flow produces f1=0 with realistic counters. The `bmak.get_telemetry()` API always returns f1=1 and counter=8888888.

3. **fpgen for fingerprint fidelity.** The `fpgen` library generates realistic browser fingerprints including 500 real audio signal floats, WebGL parameter maps, and GPU data. This lets jsdom pass Akamai's deep fingerprint validation.

4. **Forward ALL captured sensor posts.** A single jsdom run captures ~6 sensor POSTs. Forwarding all of them sequentially builds trust faster than just the first.

5. **Request routing > cookie transfer.** Route all Playwright HTTP through curl_cffi (`page.route("**/*")`). Cookie transfer between TLS stacks fails because Akamai ties `_abck` trust to TLS fingerprint.

6. **UA version must match.** The User-Agent and sec-ch-ua must reference the same Chrome version. Mismatch → 428.

7. **Verify URL returns 403 but advances state.** Parse the cookie, not the status code.

### What Failed

| Attempt | Why it failed |
|---------|---------------|
| Bundled Chromium | TLS fingerprint differs from real Chrome → 403 |
| Hardcoded UA version | sec-ch-ua auto-generated from binary version creates mismatch |
| Cookie transfer (Playwright → curl_cffi) | `_abck` trust is TLS-bound |
| `bmak.get_telemetry()` | Always returns f1=1 (sentinel for programmatic access) |
| jsdom without fpgen audio | AudioContext stubs return zeros → f1=1 |
| Sensor POST without sec-fetch headers | Server returns 201 (rejected) |
| `AKCPT.verifyStateChallenge()` alone | Doesn't advance sec_cpt past 2 |
| `AKCPT.behavioral_verify()` | Method doesn't exist at runtime |

## Protocol Notes

- **HTTP/2**: Required. Confirmed via Performance API `nextHopProtocol: 'h2'`.
- **TLS 1.3**: Through the proxy (transparent tunnel, not MITM).
- **Proxy**: French residential proxy required (Basic-Fit is EU-focused). Session stickiness maintains same exit IP.
- **Sensor POST**: `Content-Type: text/plain;charset=UTF-8`, body is `{"sensor_data":"..."}`.
